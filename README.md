# dbt in Practice — Topspin Tennis Academy

The companion repo for *dbt in Practice*, a Pearson LiveLessons course. It
built one dbt v2 project, for a fictional tennis academy called Topspin
Tennis Academy, one lesson at a time. Every lesson has a starting point, a
finished state, and a doc explaining the theory and the how-to — the
finished state of every lesson is a pre-built folder at this repo's root;
[`lesson-8-deployment/`](lesson-8-deployment/) is also this repo's one
live dbt project, the one still being developed going forward.

Nothing here is real: no real academy, no real member, no real reservation.
The data is synthetic, generated by a script you can read.

## How this repo is organized

- **`lesson-8-deployment/` is the one live dbt project.** Lessons 1-8
  were originally built by growing one dbt project in this repo's root,
  commit by commit — that history is still exactly what the git tags
  below point at. Once the course reached its last lesson, root held the
  exact same project as `lesson-8-deployment/` twice over, so the
  duplicate copy was removed in favor of just keeping
  `lesson-8-deployment/` itself as the one this repo develops going
  forward.
- **`start/` and `lesson-1-setup/` through `lesson-7-governance/` are
  pre-built, checked-in snapshots**, one per earlier lesson's finished
  state, regenerated from the tags below by
  [`scripts/build_demo_repos.sh`](scripts/build_demo_repos.sh) — open the
  one you want, nothing to run first. Each is a plain folder (no nested
  `.git`), self-contained with its own `README.md`, and — from
  `lesson-2-ai-infrastructure/` on — its own `.claude/` config and (from
  `lesson-4-development/` on) its own `scripts/`.
- **Git tags are the historical record**, one pair per lesson
  (`lesson-3-start` / `lesson-2-end` point at the exact same commit).
  `git checkout lesson-4-start` still reconstructs that exact historical
  root-project state if you want the real commit instead of the
  pre-built folder — but for just looking at or running a lesson's
  finished project, open its own folder instead.
- **Each lesson's doc *is* that lesson's `README.md`**, not a separate
  `docs/` subfolder — open any lesson folder and its README is the
  theory and how-to for that lesson specifically, not the whole
  project. Earlier docs and `AGENTS.md` (from Lesson 7 on) that cited
  another lesson's doc by path (e.g. `docs/02-ai-infrastructure.md`)
  were rewritten to link to that sibling folder's `README.md` instead —
  to read an earlier lesson's theory, open that lesson's own folder.
- **`.github/workflows/dbt-ci.yml` only exists inside
  `lesson-8-deployment/`** (CI is Lesson 8's own topic) and is reference
  material, not a live workflow — GitHub Actions only discovers
  `.github/workflows/` at a repository's *actual* root, and
  `lesson-8-deployment/` is a folder nested inside this one, not a
  GitHub repo of its own.

| Lesson | Folder (its `README.md` is the doc) | Tag (end of lesson / start of next) |
|---|---|---|
| Introduction | [`start/`](start/) | `lesson-1-start` |
| 1. Setup | [`lesson-1-setup/`](lesson-1-setup/) | `lesson-1-end` |
| 2. AI Infrastructure | [`lesson-2-ai-infrastructure/`](lesson-2-ai-infrastructure/) | `lesson-2-end` |
| 3. Sources | [`lesson-3-sources/`](lesson-3-sources/) | `lesson-3-end` |
| 4. Development | [`lesson-4-development/`](lesson-4-development/) | `lesson-4-end` |
| 5. Documentation | [`lesson-5-documentation/`](lesson-5-documentation/) | `lesson-5-end` |

— once a lesson's folder is the live project, regenerating it from its
frozen tag would overwrite real work. If you ever do want to hard-reset
it back to the tag: `git archive lesson-8-end | tar -x -C lesson-8-deployment`.

## Cheatsheets

Each lesson folder has its own quick-reference PDF, right inside the
folder, and only its own — `lesson-1-setup/cheatsheet-01-setup.pdf`
through `lesson-8-deployment/cheatsheet-08-deployment.pdf`. Commands and
config to have open while you work through that lesson, not a
substitute for its own doc's explanation.

[`scripts/cheatsheets/`](scripts/cheatsheets/) has all eight
individually, plus all eight combined
(`dbt-in-practice-cheatsheets.pdf`) — the master store
`scripts/build_demo_repos.sh` copies each lesson's own PDF from on
every rebuild, since cheatsheets aren't part of any git tag's tree.
It's a build input, not a lesson folder, so it's under `scripts/`
rather than sitting at the repo root.

## Setup

This project runs on Snowflake plus the dbt platform — see
[lesson-1-setup/README.md](lesson-1-setup/README.md) (1.1) for why,
including what that costs you versus a local-only project. The dbt
project itself lives at
[`lesson-8-deployment/`](lesson-8-deployment/) (see "How this repo is
organized" above for why there isn't a second copy anywhere else).

1. **[dbt v2](https://docs.getdbt.com/docs/fusion/about-fusion)** (the
   Fusion engine).
2. **A Snowflake account** with a warehouse, a database, and a role that
   can create schemas (`TRANSFORMER` by default — see
   [`lesson-8-deployment/profiles.yml`](lesson-8-deployment/profiles.yml)),
   plus an RSA key pair for your user — see
   [`start/scripts/load_raw_data.py`](start/scripts/load_raw_data.py)'s
   docstring for the exact commands.
3. **A dbt platform account** (the free Developer plan covers Jobs;
   Lesson 8's Admin API and some CI features need a paid Starter plan).
   Set the project's own `dbt-cloud: project-id:` in
   `lesson-8-deployment/dbt_project.yml` once you've created it.

Set these environment variables (see `lesson-8-deployment/profiles.yml`
for the exact names): `SNOWFLAKE_ACCOUNT`, `SNOWFLAKE_USER`,
`SNOWFLAKE_PRIVATE_KEY`, `SNOWFLAKE_WAREHOUSE`, and optionally
`SNOWFLAKE_ROLE` / `SNOWFLAKE_DATABASE` if you're not using the defaults.

Then, from the repo root:

```bash
pip install snowflake-connector-python pandas   # start/scripts/load_raw_data.py's own dependencies
python3 start/scripts/load_raw_data.py          # loads start/data/raw/*.csv into Snowflake's RAW schema
cd lesson-8-deployment
dbt deps                                        # once a lesson introduces a package
dbt build --profiles-dir .
```

Every `dbt` command in this repo's docs assumes it's run from
`lesson-8-deployment/` with `--profiles-dir .` (or
`export DBT_PROFILES_DIR=.` once, for the session) — `profiles.yml`
lives there, not in `~/.dbt/`, so there's nothing outside the clone to
manage beyond the credentials above. If dbt ever resolves to the wrong
project, add `--project-dir .` as well.

**Verification status:** Lessons 1-3 were originally built and verified
against a real local DuckDB project, then rewritten for Snowflake + the
dbt platform. That rewrite is correct dbt/Snowflake syntax but hasn't been
run against a real account yet — see each lesson's own doc for the same
note. Treat anything Snowflake-specific as "should work," not "confirmed,"
until it's actually been run once a sandbox exists.

### Regenerating the data

`start/data/raw/*.csv` is already committed, so the step above is all you
need. To generate a fresh (still internally consistent) dataset of your
own:

```bash
python3 start/scripts/generate_demo_data.py --seed 7 --members 300
python3 start/scripts/load_raw_data.py
```

`generate_demo_data.py` and `load_raw_data.py` only exist in `start/` —
they're a one-time step before Lesson 1, and neither does anything
without `start/data/` next to it. See the docstring at the top of
[start/scripts/generate_demo_data.py](start/scripts/generate_demo_data.py)
for what's deliberately messy in this data, and why — several quirks
exist specifically to motivate a lesson's live demo, not by accident.
